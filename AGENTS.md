# Agent Instructions

This file is the canonical source of truth for project rules, architecture, and
workflow — for both human contributors and AI agents. Agent tools that support the
`AGENTS.md` convention read it automatically. Claude Code reads [`CLAUDE.md`](CLAUDE.md)
instead when both exist, so `CLAUDE.md` imports this file; keep rules, architecture and
commands here. [`CONTEXT.md`](CONTEXT.md) is the terminology glossary, and
[`CONTRIBUTING.md`](CONTRIBUTING.md) covers the contribution workflow (local checks, tests,
and changelog fragments). Source setup and development workflows live in
[`docs/development/GETTING_STARTED.md`](docs/development/GETTING_STARTED.md) and
[`docs/development/DEVELOPMENT.md`](docs/development/DEVELOPMENT.md).

> **MANDATORY before calling any task done: write a changelog fragment.**
> **NEVER edit `CHANGELOG.md` directly.** Instead, create or update `.changelog/wip/<branch>.yaml`.
> Each entry must include `timestamp`, `title` and `description`; `title` is a changelog-ready imperative sentence, 80 characters or less, and may keep a leading `⭐` for important changes.
> Read `.git/HEAD` to get the branch name. Replace `/` with `_` for the filename. On `main`, use a new `.changelog/wip/main-<timestamp>.yaml` per session.
> Every entry must use a public release category: `added`/`changed`/`fixed`/`removed`/`security`/`breaking`. Tests, docs, CI, refactors go under the category that best matches their user-visible effect; with no public effect, leave every list empty.
> See _Changelog fragments_ below for the exact format.

Project glossary (ubiquitous language) lives in [`CONTEXT.md`](CONTEXT.md). Use it as the source of truth for terminology in code, docs, and Gherkin.

## Rules

1. **Never run any git command which pushes.** Previously caused data loss.
2. **Keep docs in sync with code.** Update the owning document in the same change as code, config, or script changes. Use the routing table under _Architecture_ below to find it, and [`docs/README.md`](docs/README.md) for the full index.
3. **Write a `.changelog/wip/<branch>.yaml` fragment with every change.** NEVER edit `CHANGELOG.md` directly — it is generated by CI. Read `.git/HEAD` for the branch name (replace `/` with `_`; on `main`, a new `main-<timestamp>.yaml` per session). Every entry must use a public release category: `added`/`changed`/`fixed`/`removed`/`security`/`breaking`. Tests, docs, CI, and refactors should be described under the public category that best matches their user-visible effect. Every entry must include `timestamp`, `title` and `description`; `title` is a changelog-ready imperative sentence, 80 characters or less, and may keep a leading `⭐` for important changes. See _Changelog fragments_ below for the exact format. **Never skip this step.**
4. **Design work = instruction file updates.** UI/UX/layout/token/component changes MUST update `AGENTS.md` and any local instruction file ([`www/default/AGENTS.md`](www/default/AGENTS.md) — see _Frontend conventions_ below) in the same change.
5. **No instruction drift.** If live UI disagrees with any instruction file, fix before calling task done.
6. **Avoid overengineering.** Smallest correct change.
7. **No temporary planning artefacts in durable files.** Do not reference AI-generated implementation plans, design notes, rollout phases, PR history, scratch docs, or orphaned requirement labels from source, tests, comments, or long-lived markdown. If context must survive, fold it into stable docs (`AGENTS.md`, `CONTEXT.md`, ADRs, user docs) as current behaviour.
8. **No code comments** unless linter-required or genuinely non-obvious. When comments are needed, describe current behavior only — never `PR 1`, `Phase 3`, `AC-1.2.3`, `REQ-3.5.1`, or similar implementation-history breadcrumbs unless they point to a stable checked-in source of truth.
9. **Single Rust binary** (`agent-stream`), source in `src/`, DashMap cache + filesystem JSON storage, Surfaces hot-reloadable. No restart unless modifying startup-only config. Runs in Active or Standby mode (`server_mode` in bootstrap config, default `active`). Readiness is `GET /api/v1/health` (200 once Active and ready, 503 otherwise); liveness is `GET /api/v1/alive` (always 200). See [`docs/CONFIGURATION_RELOAD.md#server-mode`](docs/CONFIGURATION_RELOAD.md#server-mode).
10. **The Surface is the routing unit for model traffic.** In code it is `PipeConfig` ([`src/pipes/config.rs`](src/pipes/config.rs)), served by `src/pipes/` (executor, route manager, per-type handlers). LLM and IDE Surfaces are its user-facing types (the code also keeps a `webhook` type). Read the Surface before changing pipeline behaviour. A separate internal record, `AgentSurface` ([`src/config/agent_surface.rs`](src/config/agent_surface.rs)), is what a peer appliance reaches over the Fabric, received in `src/gateways/connection_points/`; channel-shaped read accessors on it remain in `src/config/agent_surface_accessors.rs`, mapping its access-point protocol onto the `ChannelProtocol` enum that stored configs still use. See [`ARCHITECTURE.md`](ARCHITECTURE.md).
11. **"Agent Surface" is a code identifier, never a product term.** It must not appear in the dashboard, in `docs/`, or in Gherkin. Users see **Surfaces** — **LLM Surface** and **IDE Surface** — as [`CONTEXT.md`](CONTEXT.md) defines them.
12. **OPA = Regorus** (Rust-native Rego, no external process). Appliance-wide policy runs before the Surface's own policy (Trust Fabric policy on the Fabric path), and its deny is final. Each policy layer has its own Rego package and query; the wrong package fails closed. See [`docs/POLICY.md`](docs/POLICY.md).
13. **DashMap is authoritative at runtime.** Disk writes immediate. Manual `_storage/` edits to Surfaces and the other refreshed stores are picked up within `cache_refresh_interval_secs` when it is > 0; Members, Teams, Prompts, policy definitions and the other stores loaded at startup need a restart. See [`docs/CONFIGURATION_RELOAD.md`](docs/CONFIGURATION_RELOAD.md). `POST /api/v1/config/reload` rebuilds the internal surface records and rebinds listeners from `agent-stream.json`; it does not re-read Surfaces, Members, Teams or `config.toml`.
14. **Leave code better** — DRY, no dead code, single-responsibility functions.
15. **Always test** — positive and negative cases.

## Changelog fragments

Every change needs a fragment under `.changelog/wip/<branch>.yaml`. The filename uses the current branch with every `/` replaced by `_` (e.g. `feat/foo` → `.changelog/wip/feat_foo.yaml`), and the `branch:` field keeps the real branch name (with slashes). On `main`, start a new `.changelog/wip/main-<timestamp>.yaml` per session; its `branch:` is still `main`. CI generates `CHANGELOG.md` from these fragments on release — never edit `CHANGELOG.md` directly.

```yaml
branch: <current-git-branch>
changes:
  added: []
  changed:
    - timestamp: '2026-01-01T00:00:00.000Z'
      title: Describe the user-visible change
      description: Explain what changed and why.
  fixed: []
  removed: []
  security: []
  breaking: []
```

- Put each entry under the public category that best describes the change: `added` / `changed` / `fixed` / `removed` / `security` / `breaking`. Tests, docs, CI, refactors, and dependency bumps go under the category that best matches their user-visible effect.
- Keep all six category lists in the fragment. If a change has no public release effect, leave them all empty.
- `breaking` entries name the exact config key, API field, or CLI flag that changed and the migration step. `security` entries name the affected and fixed versions.
- Every non-empty entry requires an RFC 3339 `timestamp`, a `title`, and a `description`.
- `title` is a changelog-ready imperative sentence, 80 characters or less; important entries may keep a leading `⭐` (counted within the 80).
- `description` says what changed and why — never `Change description`.
- One entry per logical change. Append to the existing branch fragment if one already exists, and commit it alongside the code change.

## Build, container and quickstart

[`docs/development/GETTING_STARTED.md`](docs/development/GETTING_STARTED.md) is the public
first-run guide (Docker quickstart and source build). Keep it, the README's Quickstart
section, and [`docker-compose.yml`](docker-compose.yml) in sync with the scripts. The build
path must need no private infrastructure: public base images only, no registry login, no
internal hosts. Setup and run scripts are bash, portable to macOS and Linux: use `sedi` from
`scripts/_portable.sh`, never `sed -i ''`. How `make config-docker`, Compose, and the run
scripts work is in [`docs/development/DEVELOPMENT.md`](docs/development/DEVELOPMENT.md#docker).

## Tests

[`docs/development/TESTING.md`](docs/development/TESTING.md) sets out the layers, which one a change belongs in, and how to run them.

- **Unit**: `#[cfg(test)] mod tests` inline in each module.
- **Component**: `src/component_tests/`. Cross-module flows without Docker.
- **BDD/Gherkin**: read [`docs/testing/bdd-gherkin.md`](docs/testing/bdd-gherkin.md) before editing `.feature` files, Cucumber steps, or BDD harness code. Keep scenarios black-box, real-process, product-worded, and free of internal routing-unit names.
- **Appliance testkit**: `make test-integration` runs the end-to-end testkit in [`tests/appliance/`](tests/appliance/README.md).
- **Dashboard**: `make npm-test` for frontend unit tests, `make ui-test` for Playwright ([`ui-tests/`](ui-tests/README.md)).

## Frontend conventions

- **Every user-visible change** needs a changelog fragment — see rule 3.
- **Dashboard UI (`www/default/src/**`)** follows the existing dashboard design conventions: reuse the shared shell components, tokens, and dark theme already in the tree; keep page entry files orchestration-focused and extract sections, hooks, helpers, and local types as pages grow.

For frontend work under `www/default/`, use the scoped instructions at
[`www/default/AGENTS.md`](www/default/AGENTS.md). They cover the Surface builder elements,
the LLM configuration tab, the monitoring pages, and test identifiers; shared UI patterns
live in [`www/default/DESIGN_PATTERNS.md`](www/default/DESIGN_PATTERNS.md).

Keep this file and `www/default/AGENTS.md` in sync in the same change when UI patterns
evolve. Instruction drift is a blocker.

## Architecture

[`ARCHITECTURE.md`](ARCHITECTURE.md) is the map: the planes, the startup sequence, the
request path stage by stage, the Fabric path, the invariants, and a module map covering
every entry in `src/`. Read it before changing anything on the request path.

Three things are worth knowing before you open it.

**The Surface is the unit everything hangs off.** A request reaches a Surface's Access
Point, is authenticated, passes policy, the team gate, and the request-side guardrails, is
routed to an upstream, and its response passes the response-side stages before it is
recorded and returned. Any stage can refuse.

**Every client dialect is normalised at the front door and re-shaped at the edge.**
Requests in the Anthropic Messages or OpenAI Responses format become the OpenAI-canonical
body before the pipeline runs, and the response is converted back. See
[`docs/CLIENT_API_DIALECTS.md`](docs/CLIENT_API_DIALECTS.md).

**Policy, source authentication, and credentials fail closed.** A Surface that declares
source authentication is never served unauthenticated on its own Access Point, apart from the
read-only GETs listed in [`docs/SOURCE_AUTH.md`](docs/SOURCE_AUTH.md) (when it is dispatched from
an IDE Surface, the IDE Surface's source authentication applies instead),
a policy that cannot be evaluated denies, and a secret a Surface references is sent only
after its tenancy check passes. Choosing where a stored secret is sent needs `secrets.view`,
which can still obtain a value when `secrets.reveal_values` is `false`; that accepted
risk is recorded in
[`docs/PROVIDERS_AND_CREDENTIALS.md`](docs/PROVIDERS_AND_CREDENTIALS.md#reading-a-secret-back).

## Ways of working

### New features

1. Clarify requirements first — one question at a time. Capture durable decisions in stable repo docs only when they truly belong there.
2. Design interfaces/structure before code.
3. Incremental steps validated by unit tests.
4. Keep stable docs in sync, but do not treat temporary implementation or design plans as source of truth.
5. Unit tests must assert returned values, not just no-error.

### Commands to run

1. compile check: `cargo test --no-run 2>&1 | grep -E "^error\[E|^warning|^\s*-->|Finished"`
2. module tests: `cargo test --bin agent-stream "<module name>"`

`make test` and the other test targets prepare the test environment they need through
`make config-test`. Run `make config-test` once before invoking `cargo test` directly.

`make help` lists every target. The ones used most:

| Task | Command |
| --- | --- |
| Fast compile check | `make check` |
| Build backend and frontend | `make dev` |
| Run locally (builds www + cargo) | `make run-debug` (`x=<name>` for a named instance) |
| All Rust tests | `make test` (`test=<name>` filters) |
| Behaviour tests | `make test-bdd` |
| Frontend unit tests | `make npm-test` |
| Playwright UI tests | `make ui-test` |
| Lint with autofix (fmt check, Clippy `--fix`, ESLint `--fix`) | `make lint` |
| Format Rust and frontend | `make fmt` |
| Local CI preflight | `make ci` |

### Before ready for review

1. `make fmt-check`
2. `make clippy-ci` — fix all warnings/errors
3. `make npm-lint-ci` if `www/default/` files changed
4. `make test`
5. `make license-check` and `make audit` if dependencies changed
6. `make lint-bdd-gherkin` if `.feature` files or step bindings changed
