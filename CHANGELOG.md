## [1.0.1] - 2026-11-10

### Added

- **End dashboard sessions when someone signs out at the OpenID provider** — In OIDC mode, the provider can post a signed logout token to /oidc/backchannel-logout (OpenID Connect Back-Channel Logout 1.0). Agent Stream verifies it, requires exp, refuses a replayed jti, an ID token posted in its place and anything not signed by the provider, and ends the sessions it names: one provider session by sid, or every session of the account by sub. A Standby answers 503 so the provider retries against the Active. Each OIDC session now records the provider sign-in it came from. logout.backchannel in oidc.json turns the route off. Until the provider's discovery document has been fetched once, a failed fetch is not tried again for a minute, so requests while the provider is unreachable do not each reach it.
- **Sign out of the OpenID provider too when signing out of the dashboard** — In OIDC mode, signing out of the dashboard now also signs the person out of the provider (OpenID Connect RP-Initiated Logout 1.0): /auth/logout answers with the provider's end_session_endpoint, carrying the session's ID token as id_token_hint, and the dashboard goes there. A session that expires does not. The provider returns the browser to logout.post_logout_redirect_uri, where the login page says "You have signed out." logout.rp_initiated in oidc.json keeps sign-out local instead.
- **⭐ Sign in to the dashboard with any OpenID Connect provider** — A new sign-in mode, auth_mode = "oidc", signs dashboard users in with one OpenID provider configured in oidc.json, using the authorization code flow with PKCE, a nonce and a browser-binding cookie. The ID token is fully verified, its signature included, against the provider's published keys. Users are created on first sign-in, identified by the provider account (issuer and sub) and never by email. A claim mapping (role_mapping, a string or array claim) sets each user's role at every sign-in, raising or lowering it, and refuses unmapped accounts by default; required_claims binds the deployment to one tenant at the provider, matching string or boolean claims such as email_verified. Values in both may be regex: patterns, for example every address at one email domain, and an exact entry overrides a pattern. The client secret is a secret reference and is never written into the file. Sign-in keeps working on the cached discovery document while the provider cannot be reached.
- **Let an OpenID provider start a dashboard sign-in from its own portal** — In OIDC mode, /oidc/initiate (GET or POST) starts a fresh sign-in at the configured provider, as OpenID Connect Core section 4 describes, so a provider's portal can link people straight into the dashboard. The iss parameter must name the configured issuer, a short plain login_hint is passed on to the provider, and target_link_uri chooses where the dashboard opens, but only a dashboard page on its own origin, which the dashboard opens as it restores any deep link after sign-in; anything else opens the home page.
- **Count skipped access token, API key and identity records on load** — Management access tokens, API keys, DID:webvh identities and an unparseable dashboard settings file on promotion are now logged at ERROR and counted in agent_stream_storage_load_errors_total, labelled by entity and reason. A file that is not valid UTF-8 counts as parse_failed.
- **Count stored records skipped on load in storage_load_errors_total** — The Prometheus counter agent_stream_storage_load_errors_total, labelled by entity and reason, counts every stored record that could not be read, decrypted, parsed or migrated and was skipped, as Agent Gateway does, so a policy or gateway missing after startup or promotion can be alerted on.

### Changed

- **Refetch JWKS keys for an unknown kid at most once a minute** — A JWT naming a kid that the cached keys lack made Agent Stream fetch the JWKS again every time, so tokens with made-up kid values could make each request reach the key server. A missing kid now refetches at most once a minute for each JWT verification strategy and for OIDC sign-in, including when such tokens arrive together or the fetch fails; a rotated key is picked up within a minute of its first use.
- **Return the sign-in label from the auth mode endpoint** — GET /v1/auth/mode now returns a label field next to mode: the provider name shown on the sign-in button in OIDC mode, and null in passkey and SAML modes. Clients that read only mode are unaffected.
- **Hold a promotion at 503 when the dashboard settings file cannot be parsed** — A promoted instance now retries a settings file that cannot be parsed, including one that is not valid UTF-8, and stays at 503 until the file is fixed or restored. It logs each attempt at ERROR and counts it in agent_stream_storage_load_errors_total. Previously it went ready with its own startup copy, so the metrics endpoint's authentication and the audit switch could be served stale after a failover.
- **Report a policy edit whose engines could not be refreshed** — Updating or deleting a policy definition now answers 500, naming the definition, when the engines that reference it cannot be refreshed because the engine stores are unavailable or cannot be read. The definition is saved, but the live engines may still enforce the previous version; saving or deleting it again retries.
- **Document that unreadable stored policy records are skipped, not denied** — The policy and architecture docs now state that a policy definition or the appliance-wide assignments document that cannot be read is skipped and counted in agent_stream_storage_load_errors_total rather than failing closed, so a skipped assignments document leaves no appliance-wide policy enforced and operators should alert on that counter.

### Fixed

- **Stop dashboard log updates from reading the whole log file into memory** — A dashboard tab that asked for log entries after an old position, for example after sitting in the background or reconnecting after a restart, made Agent Stream parse every line from that position to the end of the log file before keeping the last few hundred. On a large log this spiked memory by hundreds of MB and could get the container killed for running out of memory. Agent Stream now finds the newest lines by scanning back from the end of the file and never goes back more than 8 MiB, however old the position is.
- **Keep dashboard log positions correct when a log line holds non-ASCII text** — When a tail read of the log file started inside a multi-byte character, the dashboard log tail recorded every following line at the wrong byte position, so later updates could repeat lines. Agent Stream now counts the skipped partial line in bytes.
- **Show the full number of newest log lines in the dashboard when lines are long** — The dashboard log tail read a fixed 512 bytes per requested line from the end of the log file, so with longer lines, such as JSON logs, it showed fewer lines than requested. Agent Stream now counts lines back from the end of the file, up to 8 MiB, and returns every requested line within that range.
- **Skip reading the log file for dashboard callers without logs.view** — GET /v1/dashboard/stats and GET /v1/dashboard/delta read and parsed the log file for every caller with dashboard.view and only then dropped the lines for callers without logs.view. Any dashboard user could therefore make Agent Stream read the log repeatedly. The log file is now read only for callers allowed to see it.
- **Show the level of INFO and WARN lines in the dashboard log view** — Log lines pad the level to five characters, so INFO and WARN lines carry an extra space after the timestamp. The dashboard's log parser split on that space, which left these lines with no level and put the level word at the start of the message, so level filters and colours missed them. The parser now skips the padding before reading the level.
- **Raise the user login integration event for SAML sign-ins** — SAML sign-in never received the notification store, so a SAML sign-in did not trigger the user.login integration event that a passkey sign-in triggers. Both now do, and so does OIDC sign-in.
- **Run retention sweeps and session cleanup as soon as an instance is ready** — The governance and drift retention sweeps and the expired dashboard session cleanup now run once when an instance becomes Active and ready, at startup and after every promotion (including one that happens while a run is in progress), then on their interval. Previously the retention sweeps skipped their first run, so nothing was pruned for up to six hours after each start or failover.
- **Reject management access tokens revoked on the previous Active after failover** — A promoted Standby now re-reads management access tokens before it reports ready. A token revoked on the previous Active is rejected instead of authenticating and writing its un-revoked record back to disk, and a token created or rotated there authenticates. A token used on a Standby no longer writes its last-used time, so it cannot overwrite a revocation the Active made. A token record that cannot be read holds the reload for a retry instead of dropping a valid token. Upgrade step: after upgrading, list access tokens and revoke again any that were revoked before a failover and now show as active; records written by earlier versions are read as they are stored.
- **Stop a Standby from deleting shared dashboard session files** — The periodic expired-session cleanup now runs only on the Active. A Standby used the expiry times it loaded at startup and deleted sessions the Active was still keeping alive, which signed those users out after a failover.
- **Keep OIDC dashboard users and sessions across failover** — In OIDC sign-in mode a promoted instance now re-reads the dashboard users and sessions the previous Active stored, as it does in passkey and SAML modes. Previously the first session cleanup after a failover deleted sessions the previous Active had kept alive, which signed those users out.
- **Stop a non-UTF-8 metrics file from holding a promotion at 503** — A request log or system metrics history that is not valid UTF-8 is now treated like any other unparseable file: it is logged and does not hold readiness back. Previously the promotion retried it forever and the instance stayed at 503.
- **Recompile policy engines from the existing stores and drop stale engines** — Policy engine recompiles and the policy impact count on promotion and on policy edits now use the existing internal surface record and gateway stores instead of opening new ones. Each new store started a refresh task that never stopped when cache_refresh_interval_secs is set, and an empty gateway listing saved a localhost self-gateway to shared storage. A promotion re-reads the internal surface records first, and drops the engine of a record stored as disabled and of a gateway no longer stored. A gateway this instance already enforces stays enforced when its record cannot be read and denies instead of skipping policy. A surface store that failed to open at startup is opened on the first retry that needs it and kept, and readiness is held at 503 until it opens; a gateway store that failed to open has no engines to refresh.
- **Reload shared state from disk when a Standby is promoted to Active** — A promoted Standby now re-reads Members, Teams, dashboard users and sessions, policy engines, usage and monitoring series, the request log, system metrics, dashboard settings, credential revocations, governance chains, prompts, terms, provisioning and drift records, so data written on the previous Active is kept.
- **Stop a Standby from writing shared monitoring, governance and drift state** — Metrics persistence, governance and drift retention, and drift evaluation now run only on the Active, so a Standby sharing storage no longer overwrites what the Active writes.
- **Retry a promotion when monitoring history cannot be read from storage** — A storage read error on the request log, time series, system metrics history or member provisioning config now holds readiness back and is retried, instead of starting empty and overwriting the previous Active's history on the next save.
- **Recompile every enabled Surface and gateway policy when a Standby is promoted** — Promotion now rebuilds the policy engine of every enabled Surface and gateway, not only those with a policy on the base target. A Surface whose policy comes from its default variant gets the current policy, and a gateway whose policy was removed no longer enforces it.
- **Stop a scheduled drift evaluation when its instance is demoted** — A scheduled replay evaluation still running when the instance is demoted now stops before its next session and records nothing. Previously it kept spending on the upstream and wrote drift series, evaluation state and a run record over what the new Active had stored.
- **Retry a promotion when Surfaces or gateways cannot be read for policy** — A storage error reading Surfaces, or the Surface or gateway store while policy engines are recompiled, now holds readiness at 503 and is retried. Previously the instance went ready with the policy engines it compiled at startup, and a Surface first seen on promotion had none.
- **Keep live stage streams open while a buffered surface's model writes** — A caller that sends x-agent-stream-emit-stages: true to a surface that answers whole (a Jury, a Decider, a Comparer or Summariser mode, or a response guard) received nothing between the last pre-model stage and the final result event. When the model took longer to write than the idle timeout of a load balancer or proxy in front of the appliance (60 seconds on an AWS Application Load Balancer), the connection was closed and the caller lost the answer. The stage stream now sends an SSE keep-alive comment every 15 seconds while no event is due; SSE readers ignore comments, and the stream still ends with its last event. Unit tests cover a quiet stream, no comment before the interval, and the stream ending with its events.

## [1.0.0] - 2026-11-02

### Added

- Introduce LLM Surfaces for routing and governing model calls from agents and applications.
- Introduce IDE Surfaces that offer editors one governed model catalogue behind an OpenAI-compatible endpoint.
- Support OpenAI Chat Completions, Anthropic Messages, and OpenAI Responses client APIs against any provider.
- Support OpenAI, Anthropic, Gemini, Bedrock, Azure OpenAI, Microsoft 365 Copilot, and other native and OpenAI-compatible providers.
- Support operator, tenant, and caller-supplied provider keys, with secret-backed upstream headers and billed-cost tracking per key source.
- Support Variants, routing rules, canary splits, and Decider, Comparer, and Summariser model selection.
- Support failover, load balancing, retries, circuit breakers, rate limits, and exact and semantic response caching.
- Support reasoning, structured outputs, prompt caching, and Web Search and Web Fetch server tools.
- Support image, audio, document, and realtime voice inputs.
- Support Prompt Guard sensitive-data masking with pattern and model-backed detection and NER ID pseudonymisation.
- Support Judge, Jury, and Expert Witness guardrails with categorised rejections.
- Support API key, JWT, and mTLS source authentication.
- Support layered, versioned OPA/Rego policy with dry runs and Verifiable Presentation evidence.
- Support Members, Teams, budgets, usage limits, and per-stage cost attribution.
- Support versioned, reusable prompt templates.
- Support signed, hash-chained Governance Records issued as Verifiable Credentials.
- Support LLM drift detection against pinned baselines with replay evaluation.
- Support Prometheus, OpenTelemetry, Langfuse, and live pipeline stage streaming.
- Support usage, budget, and drift alerts and events through webhook, Slack, email, Kafka, Kinesis, Pulsar, and Redis Streams integrations.
- Support a web dashboard with real-time monitoring, a Surface sandbox, and hot configuration reload.
- Support admin RBAC, passkey and SAML sign-in, scoped management access tokens, and tenant-aware management.
- Support Terms and consent acceptance for dashboard users and access token owners.
- Support appliance-wide resource limits.
- Support DID-based appliance identity and DIDComm Trust Fabric connections governed by policy.
- Support encryption at rest, encrypted backups, redacted exports, secret management, and Active/Standby deployment.
- Redact secrets and personal data from logs and telemetry.
